# how secure is supabase? considering that to be my auth option

### USER
how secure is supabase? considering that to be my auth option

### GEMINI
That is a very good question. Supabase is highly secure, but it follows a "secure-by-policy" model, meaning its security relies heavily on the developer's correct implementation of its core feature: Row-Level Security (RLS). If you use Supabase Auth, you are getting a professionally managed, open-source-based authentication system. Here is a breakdown of how secure Supabase is, and where the potential for data leaks exists (which is mostly on the developer's side). ✅ Supabase's Built-In Security Strengths The Supabase platform itself is engineered with high-level security features: Password Hashing: Supabase Auth uses the robust bcrypt algorithm to hash and salt user passwords. This means that even if an attacker gains access to the database, they only get the hashed, unreadable passwords, not the plain text passwords. Compliance: Supabase is SOC 2 Type 2 compliant and HIPAA compliant (on certain plans/configurations). This means they have been independently audited by a third party for their internal security, availability, and data protection controls. Data Encryption: All customer data is encrypted at rest (AES-256) and in transit (TLS/SSL). Security Features: They offer essential protections like Multi-Factor Authentication (MFA) for your users, configurable password strength rules, and the option to block leaked passwords using the HaveIBeenPwned API (on Pro plan and up). ⚠️ The Crucial Security Caveat: Developer Responsibility The main source of security vulnerabilities and "data leaks" in Supabase is developer misconfiguration of Row-Level Security (RLS). 1. Row-Level Security (RLS) is Not Always On The Danger: By default, when you create a new table, RLS is often disabled. If RLS is disabled on a table, anyone who has the public anon key can read, write, or modify all data in that table via the API, provided they guess the table name. Your Fix: You must explicitly enable RLS on every table that contains sensitive data and then write policies that specify exactly who can access which rows. 2. Policies Must Be Correct The Danger: Even with RLS enabled, a poorly written RLS policy can leak data. For example, a policy that says: CREATE POLICY "User can view all data" ON profiles FOR SELECT USING (true); This policy enables RLS but allows everyone (authenticated or anonymous) to select all rows, which defeats the purpose. Your Fix: Use the auth.uid() function to ensure a user can only access rows where their ID matches the owner ID: CREATE POLICY "Users can view own data" ON todos FOR SELECT USING (auth.uid() = user_id); 3. Never Use the service_role Key on the Client The Danger: Supabase provides two API keys: the anon key (public, enforces RLS) and the service_role key (secret, bypasses RLS). If you accidentally expose the service_role key in your frontend code, you are effectively giving admin/root access to your entire database to anyone who inspects your source code. Your Fix: The service_role key must only be used in secure, server-side environments (e.g., Supabase Edge Functions, a custom backend server, or a CI/CD process). 📊 Summary: How Secure is Supabase?
