Okay, let's start fresh and be incredibly precise about adding the rules for a well-rounded, Cursor-like AI experience in Continue.dev, step-by-step. This process involves two main parts: Creating the rule files (these are just text files in a specific folder). Updating your config.yaml to tell Continue.dev where to find and apply these rules. Part 1: Create the Rule Files You need to create a special directory structure inside your VS Code workspace (your project folder). These files are part of Continue.dev's configuration for your specific project, not your project's code itself. Step 1.1: Create the .continue directory In your VS Code Explorer, at the root level of your current project (where your main.py or src folder usually is), create a new folder named .continue. Make sure it has the dot at the beginning! This often makes it a hidden folder, which is ideal. Step 1.2: Create the rules subdirectory Inside the newly created .continue folder, create another new folder named rules. So your path should now look like: YOUR_PROJECT_ROOT/.continue/rules/ Step 1.3: Create the Rule Markdown (.md) Files Now, create the following four .md files inside the YOUR_PROJECT_ROOT/.continue/rules/ directory. Rule File 1: 01-universal-code-quality.md This rule provides general coding standards that apply to any programming language. --- name: Universal Code Quality --- # Universal Code Quality Standards for AI Assistant This rule provides general coding practices for the AI to follow, applicable across various programming languages. **Instructions for the AI:** 1. **Readability & Maintainability:** Prioritize clear, concise, and easily understandable code. Avoid overly complex or "clever" solutions when simpler, more maintainable alternatives exist. 2. **Comments & Documentation:** Always include comprehensive comments and documentation (e.g., docstrings, JSDoc, inline comments) for all functions, methods, classes, and complex code blocks. Explain their purpose, parameters, return values, and any non-obvious logic. 3. **Naming Conventions:** Use descriptive and unambiguous names for variables, functions, and classes. Names should clearly reflect the entity's purpose. 4. **Modularity & Single Responsibility:** Break down large functions, methods, or modules into smaller, more focused units. Each unit should ideally have a single, well-defined responsibility. 5. **Consistency:** Adhere to the existing code style, formatting, and conventions of the surrounding codebase. If a specific style guide is used (e.g., PEP8, ESLint), follow it strictly. 6. **Simplicity:** Prefer simpler algorithms and data structures unless the problem explicitly demands complexity for performance or other critical reasons. 7. **Immutability:** Favor immutable data structures and pure functions where appropriate to reduce side effects and improve predictability. Rule File 2: 02-error-handling-principles.md This rule focuses on robust error handling, generally applicable to any language. --- name: Robust Error Handling Principles --- # Robust Error Handling Guidelines This rule instructs the AI on general best practices for error management, applicable across different languages. **Instructions for the AI:** 1. **Specificity:** Implement specific error handling mechanisms. Catch precise exception types or error codes rather than generic ones, to allow for targeted recovery or logging. 2. **Informative Logging:** Provide comprehensive error logging. Log the full call stack/traceback, relevant variable states, timestamps, and contextual information that aids in debugging. 3. **User Experience:** If an error might be visible to an end-user, ensure the message is clear, concise, and helpful, avoiding technical jargon where possible. 4. **Graceful Degradation:** Design code to degrade gracefully in the face of errors, preventing complete application crashes and minimizing impact where possible. 5. **External Interactions:** For operations involving external systems (e.g., network requests, database connections, file I/O), consider and suggest appropriate retry mechanisms (e.g., with exponential backoff) and timeouts to handle transient failures. Rule File 3: 03-comprehensive-testing-principles.md This rule provides universal guidelines for testing. --- name: Comprehensive Testing Principles --- # Comprehensive Testing Principles This rule guides the AI in generating and suggesting unit and integration tests. **Instructions for the AI:** 1. **Test Coverage:** Encourage the addition of appropriate tests (unit, integration) for all new or modified functionality. 2. **Test Cases Variety:** Include test cases that cover: * **Happy Path:** Typical, expected usage scenarios. * **Edge Cases:** Boundary conditions (e.g., empty inputs, maximum/minimum values, zero, null/undefined inputs). * **Error Conditions:** How the code behaves when invalid input is provided or exceptions/errors are expected. 3. **Test Independence:** Each test should be independent and produce consistent results regardless of the order in which tests are run. 4. **Descriptive Names:** Use clear and descriptive names for test functions/methods that indicate what they are testing and under what conditions. 5. **Mocking & Stubbing:** Utilize mocks, stubs, or fakes for external dependencies (e.g., database calls, API requests, file system interactions) in unit tests to ensure isolation and faster execution. Rule File 4: 04-python-specific-conventions.md This rule is only for Python files. --- name: Python Specific Conventions --- # Python Specific Coding Conventions This rule provides Python-specific guidance for the AI, complementing the universal rules. **Instructions for the AI:** 1. **PEP8 Compliance:** Always adhere strictly to the PEP8 style guide for Python code formatting and conventions. 2. **Type Hinting:** Consistently apply type hints for function parameters and return values to improve code clarity and enable static analysis. 3. **Comprehensions:** Prefer list, dictionary, and set comprehensions for creating collections where appropriate, for concise and readable code. 4. **Context Managers:** Use `with` statements for resource management (e.g., file I/O, locking) to ensure proper setup and teardown. 5. **F-Strings:** Prefer f-strings for string formatting over older methods like `%` or `.format()`. 6. **Virtual Environments:** Assume and promote practices compatible with development within isolated virtual environments. Rule File 5: 05-js-ts-best-practices.md (Optional, but good for well-roundedness) This rule is only for JavaScript/TypeScript files. Create this if you want the LLM to have specific JS/TS guidance. --- name: JavaScript & TypeScript Best Practices --- # JavaScript & TypeScript Best Practices This rule provides specific guidelines for JavaScript and TypeScript development. **Instructions for the AI:** 1. **`const` and `let`:** Favor `const` and `let` for variable declarations; avoid `var`. 2. **Arrow Functions:** Use arrow functions for concise syntax and lexical `this` binding, especially for callbacks. 3. **Documentation (JSDoc/TSDoc):** Implement JSDoc or TSDoc comments for functions, classes, and interfaces to enhance documentation and tooling. 4. **Strong Typing (TypeScript):** For TypeScript, ensure explicit and strong typing for variables, function arguments, and return values. Define interfaces or types for complex object shapes. 5. **Asynchronous Code:** Use `async/await` for modern asynchronous programming. 6. **Module System:** Adhere to ES Modules (`import`/`export`) for modular code. Part 2: Update Your ~/.continue/config.yaml Now, open your ~/.continue/config.yaml file (it's typically in your user home directory, e.g., C:\Users\YourUser\.continue\config.yaml on Windows, or ~/.continue/config.yaml on Linux/macOS). Replace your entire customRules section with the one below. Ensure it's correctly indented. # ... (your existing models, temperature, completionParams, contextProviders sections go here, as previously defined) ... # --- RULES (Defined by referencing the .md files you just created) --- customRules: - name: Universal Code Quality filepath: .continue/rules/01-universal-code-quality.md alwaysApply: true # This means these rules will always be active for every AI request description: "Core coding guidelines for readability, comments, and structure applicable to any language." - name: Robust Error Handling Principles filepath: .continue/rules/02-error-handling-principles.md alwaysApply: true description: "Principles for implementing robust and specific error handling across any language." - name: Comprehensive Testing Principles filepath: .continue/rules/03-comprehensive-testing-principles.md alwaysApply: true description: "Universal guidelines for writing effective unit and integration tests." - name: Python Specific Conventions filepath: .continue/rules/04-python-specific-conventions.md alwaysApply: true globs: "**/*.py" # This rule only applies when the active file is a Python file description: "Specific style and best practices for Python development (e.g., PEP8, type hinting)." - name: JavaScript & TypeScript Best Practices filepath: .continue/rules/05-js-ts-best-practices.md alwaysApply: true globs: "**/*.{js,jsx,ts,tsx}" # This rule only applies to JS/TS files description: "Specific guidelines for JavaScript and TypeScript development." # --- PROMPTS (Defined by referencing the .md files in .continue/prompts/) --- # Make sure these prompt files exist in YOUR_PROJECT_ROOT/.continue/prompts/ customPrompts: - name: Generate Tests filepath: .continue/prompts/generate-tests.md - name: Refactor Code filepath: .continue/prompts/refactor-code.md - name: Explain Code filepath: .continue/prompts/explain-code.md Final Actions: Save all the new .md rule files you created. Save your updated ~/.continue/config.yaml file. Restart VS Code. This is crucial for Continue.dev to pick up all the new rule files and configurations. Confirm Indexing: After restarting, Continue.dev might do some background indexing (especially if @codebase is new or changed). Let this complete. Now, when you interact with Continue.dev, the LLM will be guided by these rules. The "Universal" rules will always apply, and the language-specific ones will automatically kick in when you're working in a Python file, a JavaScript file, etc., providing that well-rounded, context-aware, Cursor-like experience.
