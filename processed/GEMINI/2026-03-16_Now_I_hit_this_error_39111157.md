### GEMINI
The shim_lock_verifier error in that black screen means your motherboard has successfully verified the first part of the bootloader, but that bootloader (GRUB) is now blocking the next step because it thinks the "Shim" or the Kernel it's trying to load isn't authorized. Basically, you’re in a "half-signed" state. Your BIOS trusts the bootloader, but the bootloader doesn't trust the rest of the OS. The Fix: Signing the "Ghost" Files Since you still have some GRUB files hanging around (as seen in your previous sbctl verify output), we need to make sure every single path the BIOS might take is signed. Boot back into CachyOS (Disable Secure Boot in BIOS again). Sign the leftover GRUB files that we saw earlier: sudo sbctl sign -s /boot/EFI/GRUB/grubx64.efi sudo sbctl sign -s /boot/grub/x86_64-efi/core.efi sudo sbctl sign -s /boot/grub/x86_64-efi/grub.efi Sign the Limine helper (just in case): sudo sbctl sign -s /boot/EFI/limine/limine_x64.efi The "Nuke" Option for Secure Boot If signing those files still gives you that shim_lock error, it’s because GRUB is trying to use a "Shim" that isn't compatible with your custom keys. If the commands above don't work, do this: Run sudo sbctl verify. Every single file that starts with /boot/EFI/ and has a red ✗ next to it MUST be signed. Use sudo sbctl sign -s [copy-paste-the-red-path-here] for every single one. Do not worry about the Microsoft files; your BIOS already trusts those because of the -m flag we used earlier. Why this is happening You have multiple bootloaders installed (Limine and GRUB). When you turn on Secure Boot, the BIOS picks one, but that one might be trying to load files from the other one. By signing every .efi file in your /boot partition, you remove any "weak links" in the chain. Go ahead and sign those three GRUB files listed in step 2 and reboot with Secure Boot on. Does that get you past the "grub rescue" screen?
